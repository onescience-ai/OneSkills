# 分步编码工作流

本文档是 `onescience-coder` 的唯一详细执行流程文档。智能体应按本文档完成资源获取、步骤规划、执行信息输出、确认后编码、下一步交接与最终验证。

## 1. 总体原则

- 先取资源，再规划，再分步执行；不要直接开始写代码。
- 每个步骤都必须先输出执行信息，等待用户确认后再执行。
- 每个步骤只实现当前已确认内容，不顺手扩展后续步骤。
- 编码依据只能来自资源技能返回的 `content` 与用户明确提供的可用内容，不能沿资源 `path` 直接读文件。
- `resource_retrieval_request` 是内部控制消息；不得把裸请求 YAML 作为对用户的最后输出。构造请求后必须继续获得 `resource_retrieval_result`，再进入初始资源筛选。
- 优先复用已有实现与适配路径；只有复用不足时，才做最小必要改造。
- 若资源不足、契约冲突或关键决策未确认，停止并补资源或询问用户，不猜测实现。
- 所有步骤完成后，统一进入最终验证：本地可冒烟则冒烟，否则静态检查。
- 冒烟测试只允许在当前环境已经具备最小运行条件时执行；不得为了冒烟测试安装 conda 环境、创建新环境或安装额外依赖包。

## 2. 强制资源获取

### 2.1 接收任务

输入来自 orchestrator 或用户：

```yaml
coding_handoff:
  task_goal: <编码任务目标>
  reference_resources:
    - path: <资源路径>
      type: <资源类型>
      content: <资源内容摘要或完整内容>
```

### 2.2 立即调用资源技能

接收任务后，必须立即调用 `type=resource` 技能获取：
- 规格知识
- 使用知识
- 规划决策知识

无论上游是否已提供 `reference_resources`，都不能跳过这一步。

如果宿主环境没有原生 skill 调用工具，则按目标 `type=resource` 技能的 `SKILL.md` 在同一轮内内联完成召回，并把得到的 `resource_retrieval_result` 作为本技能后续输入。不要要求用户手动复制请求或另起一轮检索。

### 2.3 资源调用规则

- 查询中应带上用户需求，以及从 `reference_resources` 中提取的资源名称和关键概念。
- 资源不足时，可在步骤级再次调用 `type=resource`。
- 资源 `path` 仅用于标识，不得直接读取对应文件。

输入格式：

```yaml
resource_retrieval_request:
  user_request: <用户实现需求或当前步骤需求>
  task_state_summary: <当前任务状态摘要>
  content_request: "规格知识、使用知识和规划决策知识"
  filters:
    domain: <领域过滤，可选>
    keyword: <关键词过滤，可选>
```

输出格式：

```yaml
resource_retrieval_result:
  status: success | partial | failed
  matched_resources:
    - type: <具体资源类型>
      path: <资源路径>
      name: <资源名称>
      why_matched: <匹配理由>
      limitations: <使用限制>
      content: <完整的结构化内容或文本>
```

## 3. 初始资源筛选

把上游 `reference_resources` 与本轮 `matched_resources` 合并为初始资源清单，并完成一次筛选：

1. 识别任务核心目标。
2. 为每个资源判断与当前目标的关系。
3. 将资源标记为：
   - 核心资源：当前任务必须使用
   - 参考资源：可能有用，按步骤使用
   - 无关资源：当前不使用
4. 说明为什么选择某个资源、为什么不使用另一个资源。
5. 形成资源使用清单，并标记每类资源预计在哪些步骤中使用。

## 4. 目录结构与步骤规划

### 4.1 目录结构规划

- 用户指定目录或文件时，优先遵守。
- 用户只要求单文件时，可跳过目录规划。
- 未指定时，根据资源内容和任务目标规划最小完整结构。
- 不套用固定模板，不过度设计。

输出时应明确：
- 每个目录/文件的职责
- 哪些文件新增，哪些修改，哪些保持不变
- 文件之间的依赖关系

### 4.2 步骤定义与依赖识别

一个“步骤”应满足以下要求：
- 有清晰目标
- 有明确输入/输出或接口边界
- 可以独立确认
- 完成后能为后续步骤提供依赖

不要把整个任务当成单一步骤，也不要把没有独立价值的微小编辑拆成单独步骤。

步骤规划时要明确：
- 哪些步骤独立
- 哪些步骤依赖前置输出
- 正确执行顺序
- 如果用户指定顺序与依赖冲突，应指出冲突并说明建议顺序

## 5. 每步执行前的执行信息

每个步骤开始写代码前，必须先做步骤级资源评估，再输出执行信息。

### 5.1 步骤级资源评估

对当前步骤：
1. 识别本步骤需要的知识、接口、工具与实现依据。
2. 从初始资源清单中筛选出本步骤相关资源。
3. 说明每个资源在本步骤中的用途。
4. 判断当前资源是否足以支撑实现。
5. 若不足，则调用 `type=resource` 补充资源后再继续。

### 5.2 执行信息模板

资源就绪后，输出如下结构等待用户确认：

```md
【当前编码步骤】
- 步骤编号：
- 步骤名称：
- 前置依赖：
- 本步骤目标：

【资源依据】
- 本步骤使用资源：
- 筛选理由：
- 暂不使用资源：
- 本步骤补充资源：

【详细执行信息】
- 任务类别（data / model / component / config）：
- 复用判断：
- 最小改造路径：
- 输入定义：
- 输出定义：
- 变量组织方式：
- 保持不变的部分：
- 计划新增文件：
- 计划修改文件：
- 推荐复用的组件 / datapipe / model / tool：
- 主干结构：
- 实现方法：
- 主要 shape 变化：
- 当前步骤风险点：
- 需要用户确认的关键点：

## 待确认摘要
- 本步骤将做什么：
- 当前步骤属于哪类任务：
- 复用哪些现有实现：
- 最小改造路径：
- 将写入哪些文件：
- 不会修改哪些部分：
- 后续依赖：

## 用户操作
请回复：
1. `确认，执行本步骤`
2. `修改后再执行：<修改意见>`
```

## 6. 用户确认后的执行规则

用户确认当前步骤后：

1. 开始写代码前，必须已读取 `coding_conventions.md`。
2. 只实现当前已确认步骤，不顺手实现后续步骤。
3. 严格按照确认的文件清单和接口实现。
4. 优先复用已有实现、组件与适配路径；只有复用不足时，才做最小必要改造。
5. 使用资源 `content` 作为实现依据；`path` 只用于标识，不用于直接读取资源文件。
6. 若发现资源命名、内容或契约与目标实现不一致，停止并询问，不要猜测。
7. 保持改动范围最小，只触碰当前步骤声明的文件。
8. 在没有运行证据前，不得声称“已验证通过”。

## 7. 下一步骤交接

当前步骤完成后，如果还有后续任务：

- 输出当前步骤完成摘要。
- 输出下一步骤的执行信息。
- 等待用户确认后再继续。

不要自动生成下一步骤代码，除非用户明确一次性确认了多个具体步骤。

> **autonomous_mode 例外**：当上游 `step_handoff.execution_flags.autonomous_mode` 为 `true` 时，跳过本节的确认等待。当前步骤完成后，直接输出简短完成摘要（1-2 行），然后立即进入下一步骤编码，不等待用户回复。

## 8. 所有步骤完成后的最终验证

所有编码步骤完成后，必须进行一次最终验证。

### 8.1 全路径冒烟测试分支（Full-Path Smoke Test）

仅当当前本地环境可直接运行目标代码且具备最小必要前提时，才进入本地冒烟测试分支。

**必须依次执行的检查项**（任一项失败则停止后续、记录原因并修复后再重试）：

| 序号 | 检查项 | 验证方法 | 超时 | 通过标准 |
|---|---|---|---|---|
| 1 | forward_pass | `out = model(data)` 或等效的单次前向调用 | 30s | 不报错，输出 tensor shape 与预期一致 |
| 2 | backward_pass | `loss = criterion(out, target); loss.backward()` | 30s | backward 不报错，梯度非 None |
| 3 | train_loop_dry_run | 完整训练循环 1 epoch：数据加载 + forward + backward + optimizer.step + loss 记录 | 120s | 不报错，loss 为有限数值（非 NaN/Inf），loss 整体趋势递减 |
| 4 | validation_loop_dry_run | 完整验证循环 1 batch：数据加载 + forward + 指标计算 | 60s | 不报错，指标为有限数值 |
| 5 | domain_metric_dry_run | 执行论文核心指标的计算入口（如 CFD 面板法 CL、生信 pLDDT、材料能量/力），至少检查所需数据的可达性 | 30s | 不报错 或 返回明确的不可计算原因（如 `no_surface_points`、`missing_field`）并附带说明 |
| 6 | config_consistency | 检查 params.yaml / 配置文件中的维度（encoder/decoder channel list）与模型定义一致 | — | encoder[-1] == decoder[0] 等 shape 不冲突 |

执行规则：
1. 按序号顺序执行，任一项 fail → 记录失败原因 → 修复代码 → 从失败的检查项重新开始
2. 总尝试次数（从检查项 1 重新开始的次数）不超过 6 次
3. 每次失败后，只有在已识别到明确可修正偏差时，才允许回改后再次尝试
4. 达到 6 次上限后仍失败 → `status: failed`，禁止标记为 `success`
5. **以上 6 项全部 PASS 后，才允许进入 SLURM 提交或远程执行**。不得跳过任何一项
6. 最终结果必须记录：每项 pass/fail 状态、总尝试次数、使用的本地入口/命令、结论

**autonomous_mode 下的额外约束**：即使 `execution_flags.autonomous_mode == true`，本节的 6 项全路径冒烟检查仍必须完整执行。冒烟测试失败不得静默跳过进入下一步——必须修复后重试，直至全部通过或达到 6 次上限。

**SLURM 环境下的冒烟测试执行优化**（适用于登录节点 / 计算节点分离的集群）：

1. **优先使用 `sbatch --wait`**：直接用 `sbatch --wait smoke_job.sh` 提交冒烟作业。`--wait` 会让 sbatch 阻塞直到作业完成，返回 exit code 即表示作业结束。无需手动 `sleep + sacct` 轮询。

   ```bash
   # 推荐写法
   sbatch --wait smoke_job.sh && echo "PASS: smoke test completed" || echo "FAIL"
   ```

2. **若 `--wait` 不可用，使用 `srun`（仅限极短作业）**：对于 forward_pass / backward_pass（30s 内），可优先尝试 `srun` 交互式执行，直接在计算节点上运行并返回输出。

   ```bash
   # 仅用于 30s 内的检查项
   srun -p <partition> --gres=dcu:1 python smoke_test.py
   ```

3. **自适应轮询（兜底方案）**：若 `sbatch --wait` 和 `srun` 均不可用，使用短间隔自适应轮询替代固定长睡眠：
   - 每次 sleep **不超过 10 秒**，然后用 `sacct -j <jobid>` 检查状态
   - 总轮询预算不超过检查项超时的 **2 倍**（如 forward_pass 超时 30s → 轮询预算 60s）
   - **严禁使用 90-110 秒的固定 sleep**，这浪费了大量等待时间

   ```bash
   # 自适应轮询示例（替代 sleep 90）
   for i in $(seq 1 20); do
     sleep 5
     state=$(sacct -j $JOBID --format=State --noheader 2>/dev/null | head -1 | tr -d ' ')
     case "$state" in
       COMPLETED) echo "PASS"; break ;;
       FAILED|TIMEOUT|CANCELLED) echo "FAIL ($state)"; break ;;
     esac
   done
   ```

4. **避免在登录节点执行大型命令**：登录节点通常无 GPU/DCU 驱动，不要在上面执行 `find / -maxdepth 6`、`import torch` 等会超时的命令。需要运行代码时始终通过 SLURM 提交到计算节点。

### 8.2 静态需求一致性检查分支

若本地环境不支持最小冒烟测试，则执行 `static_requirement_review.md` 定义的静态需求一致性检查。

执行规则：
1. 从用户原始需求、已确认的执行信息、上游 handoff 与资源内容中提取需求清单。
2. 逐条检查生成或修改的代码是否满足需求清单。
3. 若发现偏差，先修改代码，再重新执行静态检查。
4. 输出 `静态需求一致性检查结果`。

若未进入本地冒烟测试分支，不得声称已经完成运行验证。

## 9. 特殊场景

### 用户指定完整目录结构

完全遵守用户给定结构。若资源契约建议不同结构，只说明差异和影响，不擅自改目录。

### 用户指定要写入的文件

只写入用户指定文件和必要的直接依赖文件。需要额外文件时，先在执行信息中请求确认。

### 用户要求“一次性全部生成”

仍先给出目录结构、步骤划分和每步执行信息。只有当用户明确确认“一次性执行全部步骤”后，才可以连续编码；每步完成后仍要统一进入最终验证。

### Paper2Code

如果任务是论文复现但没有上游 `onescience-paper-repro` 的 `coder_task_description.md`，退回论文复现前处理；不要自行搜索、下载或参考官方/第三方代码仓库。

### 自主执行模式（Autonomous Mode）

当上游 `step_handoff.execution_flags.autonomous_mode` 为 `true` 时：

1. **跳过步骤确认**：不执行第 5 节的用户确认流程（即不输出"用户操作"确认请求块，不等用户回复）。仍输出执行信息摘要（步骤编号、名称、目标、文件清单，3-5 行），然后直接开始编码。

2. **连续执行所有步骤**：当前步骤完成后，按第 7 节的 autonomous_mode 例外规则直接进入下一步骤，逐步骤完成编码，直到所有步骤完成。

3. **执行信息简化**：每步只输出步骤编号、名称、目标、文件清单（3-5 行），不输出完整的资源评估和详细执行信息模板。

4. **失败处理**：若任一步骤编码遇到无法自动解决的问题（资源内容不足、接口冲突、不可自动决策的设计选择），返回 `status: blocked` 并说明具体原因，不静默跳过或猜测实现。

5. **始终执行最终验证**：所有步骤完成后，必须执行第 8 节的最终验证（冒烟测试或静态需求一致性检查）。
