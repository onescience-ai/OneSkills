# CLI 非交互执行故障分类与诊断

## 适用范围

面向命令行接口（CLI）程序在自动化、批处理或远程作业环境中的非交互执行场景，提供故障分类体系、退出码语义解读、标准错误流解析方法与错误恢复策略。适用于需要在 CI/CD 流水线、SLURM 作业调度、容器化执行或远程 SSH 环境中可靠运行 CLI 工具并快速定位其失败原因的场景。不适用于交互式终端调试或图形界面程序的错误诊断。

## 输入

- CLI 程序的退出码（exit code）
- 标准错误流（stderr）内容
- 标准输出流（stdout）内容（可选）
- 执行环境信息（操作系统、shell 类型、资源限制）
- 超时配置与实际执行时长

## 输出

- 故障分类结果（成功/用法错误/运行时错误/信号终止/资源限制）
- 根因分析报告
- 修复建议与恢复策略

## 流程节点

### Step 1：退出码捕获与初步分类
- **操作**：捕获 CLI 程序退出码，按标准语义分类
- **参数**：退出码范围 = 0-255（8位限制）
- **工具**：Shell 内置变量 `$?`（bash）、`%ERRORLEVEL%`（Windows CMD）、`process.exitCode`（Node.js）
- **质量门禁**：退出码非空且为整数

### Step 2：标准错误流解析
- **操作**：捕获并解析 stderr 输出，提取错误模式
- **参数**：错误关键词库（如 "Error", "Exception", "Permission denied", "No such file"）
- **工具**：`grep`、`awk`、正则表达式匹配
- **质量门禁**：stderr 内容可读且包含可识别的错误模式

### Step 3：环境上下文检查
- **操作**：检查执行环境是否满足程序需求
- **参数**：依赖库版本、文件权限、网络连接、磁盘空间、内存限制
- **工具**：`ldd`（动态库检查）、`df`（磁盘）、`free`（内存）、`ulimit`（资源限制）
- **质量门禁**：环境检查完成且结果明确

### Step 4：超时与资源限制检测
- **操作**：判断程序是否因超时或资源限制被终止
- **参数**：超时阈值、内存限制、CPU 时间限制
- **工具**：`timeout` 命令、SLURM 作业日志、Docker 容器限制
- **质量门禁**：超时/资源限制信息完整

### Step 5：故障归因与修复建议生成
- **操作**：综合以上信息生成结构化诊断报告
- **参数**：故障分类规则表、修复建议库
- **工具**：规则引擎、LLM 辅助推理（可选）
- **质量门禁**：诊断报告包含故障类型、根因、修复建议

## 关键参数

### 通用判据

| 参数 | 值 | 来源 | 说明 |
|------|-----|------|------|
| 退出码 0 | 成功 | [D1] | 程序正常退出 |
| 退出码 1-125 | 通用错误 | [D1] | 程序自定义错误码 |
| 退出码 126 | 命令不可执行 | [D1] | 文件权限不足或非可执行文件 |
| 退出码 127 | 命令未找到 | [D1] | PATH 中无此命令 |
| 退出码 128+N | 信号终止 | [D1] | 程序被信号 N 终止（如 130=SIGINT） |
| 退出码 130 | SIGINT (Ctrl+C) | [D1] | 用户中断 |
| 退出码 137 | SIGKILL (9) | [D1] | 强制终止（通常为 OOM） |
| 退出码 255 | 退出码溢出 | [D1] | 实际退出码对 256 取模 |

### 校准数值

以下数值来自典型 Linux 环境，供量级校准；其他操作系统或 shell 环境需以自身证据重新锚定。

| 参数 | 值 | 来源 | 说明 |
|------|-----|------|------|
| 超时退出码 | 124 | [D2] | `timeout` 命令超时返回值 |
| 资源限制退出码 | 137 | [D2] | OOM killer 终止进程 |
| Shell 语法错误退出码 | 2 | [D1] | bash 语法错误 |

## 边界与分流

### 前提：CLI 程序遵循 POSIX 退出码约定
- **不成立时**：某些程序使用非标准退出码（如 Java 用 1 表示所有错误），需查阅程序文档获取退出码语义
- **改道方案**：查阅程序官方文档或源码中的退出码定义

### 前提：stderr 流包含错误信息
- **不成立时**：程序可能将错误信息输出到 stdout 或日志文件
- **改道方案**：检查 stdout 和日志文件，或使用 `strace` 跟踪系统调用

### 前提：执行环境信息可获取
- **不成立时**：沙箱环境可能限制系统信息获取
- **改道方案**：使用容器内预装的诊断工具，或请求环境管理员协助

### 前提：超时配置合理
- **不成立时**：超时阈值过短导致误判，过长导致资源浪费
- **改道方案**：根据历史执行时间动态调整超时阈值，或使用自适应超时策略

## 质量检查

- 退出码捕获成功且在 0-255 范围内
- stderr 解析结果包含可识别的错误模式
- 环境检查覆盖程序依赖的关键资源
- 故障分类与退出码/错误模式一致
- 修复建议具体可执行

## 回退策略

1. **退出码无法解释**：使用 `strace` 或 `dtrace` 跟踪系统调用，定位底层错误
2. **stderr 为空**：检查程序是否将错误信息重定向到文件，或使用 `script` 命令记录完整终端输出
3. **环境信息不足**：请求环境管理员提供完整环境快照或容器镜像信息
4. **超时判断不确定**：使用性能分析工具（如 `perf`、`gprof`）定位性能瓶颈
