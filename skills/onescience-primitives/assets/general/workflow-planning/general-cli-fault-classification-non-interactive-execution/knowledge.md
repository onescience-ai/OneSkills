# CLI 非交互执行与故障分类

## 适用范围
适用于需要非交互执行命令行工具的自动化工作流，包括归因分析、数据处理、模型训练等场景。当任务依赖 CLI 进程且需要自动处理执行失败时，本卡片提供故障分类、退出码解读和恢复策略。

## 输入
- 命令行参数序列
- 环境变量配置
- 超时时间设置（秒）
- 沙箱或容器配置（可选）
- 重试策略参数

## 输出
- 进程退出码（整数）
- 标准输出（stdout）内容
- 标准错误（stderr）内容
- 执行日志文件路径
- 故障分类结果（成功/超时/错误/异常）

## 流程节点
1. **命令构建** → 根据任务需求组装命令行参数，确保非交互模式（如添加 `--non-interactive` 标志）。
2. **执行启动** → 使用子进程模块（如 Python subprocess）启动命令，设置超时和管道。
3. **状态监控** → 实时检查进程状态，捕获超时信号。
4. **故障分类** → 根据退出码和错误输出将故障分为：成功（0）、可恢复错误（1-125）、致命错误（126-1255）、信号终止（128+信号值）。
5. **恢复/重试** → 根据故障类别执行重试、回退或终止策略。

## 关键参数
| 参数 | 值 | 来源 | 说明 |
|------|-----|------|------|
| 成功退出码 | 0 | [D1] | 命令正常完成 |
| 可恢复错误码 | 1-125 | [D1] | 临时性错误，可重试 |
| 致命错误码 | 126-1255 | [D1] | 配置或权限问题，需人工干预 |
| 信号终止码 | 128+信号值 | [D1] | 进程被信号终止（如 SIGTERM=143） |
| 默认超时 | 300秒 | 实践值 | 根据任务复杂度调整 |
| 最大重试次数 | 3 | 实践值 | 避免无限循环 |

## 边界与分流
- **退出码 0** → 流程成功，继续下一步。
- **退出码 1-125** → 可恢复错误，根据错误类型决定重试或使用备用命令。
- **退出码 126-1255** → 致命错误，终止流程并记录诊断信息。
- **退出码 >255** → 可能为信号终止，检查进程被何种信号终止。
- **超时** → 强制终止进程，分类为超时错误，检查资源限制或任务复杂度。

## 质量检查
- 验证退出码在预期范围内（0 或已知错误码）。
- 检查标准错误输出是否包含关键错误信息。
- 确认超时设置合理（不导致过早终止）。
- 验证日志文件完整记录执行过程。

## 回退策略
- 可恢复错误：自动重试，指数退避。
- 致命错误：终止流程，生成诊断报告，通知人工干预。
- 超时：增加超时时间或优化任务分解。
- 未知错误：记录详细日志，回退到默认配置。

## 补充证据：CLI 最佳实践与退出状态值定义

[B1] Georgeson et al. (2019) 开发了 Bionitio 工具，自动化创建遵循最佳实践的生物信息学软件项目。关键特性包括：命令行参数解析、错误处理、进度日志、定义退出状态值、测试套件、版本号、标准化打包、用户文档、代码文档、开源许可证、版本控制、容器化。退出状态值定义为常量，零表示成功，非零表示错误，非零退出状态值可提供调试信息，区分不同类别的错误。错误消息写入标准错误设备（stderr）[7]。

[B2] Bionitio 遵循 Unix 惯例，包括提供帮助和版本参数，单破折号表示短参数名，双破折号表示长参数名。`--help` 参数显示用法信息，包括每个参数的描述和预期参数。输入可以来自多个文件或标准输入设备（stdin），输出写入标准输出设备（stdout），制表符分隔格式。错误消息写入标准错误设备（stderr）[7]。

[B3] Bionitio 包含单元测试和集成测试示例。单元测试在隔离环境中运行单个方法，集成测试确保程序作为整个实体正常工作。持续集成测试在每次提交时自动执行测试，有助于更快地发现问题[7]。

## 补充证据：黑箱差分测试与 CLI 生成基准
[4] Hu et al. (2026) 引入 CLI-Tool-Bench 基准，使用黑箱差分测试框架评估 CLI 工具生成质量。该框架在隔离沙箱中执行生成的 CLI 工具，将系统级副作用和终端输出与人类编写的参考进行多层级等价比较。评估显示顶级 LLM 的整体成功率仅 43.8%，表明 CLI 工具的端到端生成仍极具挑战性。该基准覆盖 94 个真实仓库、多种编程语言和复杂度级别 [4]。

## 补充证据：自愈恢复框架与故障检测
[5] Aribe & Oracion (2026) 提出基于 MAPE-K 模型的自愈框架，集成 AutoFix 机制实现自适应故障恢复。在 20 种运行时故障场景（含服务崩溃、内存泄漏、数据库断连）的受控故障注入实验中，故障检测 F1 分数达 90.7%，恢复成功率达 93.2%。AutoFix 模块将平均恢复时间（TTR）缩短 56.2%，平均恢复时间 3.92 秒。迭代反馈机制在多轮循环中提升恢复效率 18.6% [5]。

## 补充证据：科学工作流 I/O 监控与任务关联
[6] Witzke et al. (2024) 提出科学工作流的低级别 I/O 监控方法，通过关联底层 trace 数据与工作流任务日志，实现逻辑任务级别的 I/O 分类。该方法利用 Kubernetes 容器管理的元数据确保信息链完整，可揭示工作流中最昂贵或最低效的任务，为优化提供依据 [6]。
