# CLI 非交互执行与故障分类

## 适用范围
适用于在无用户交互的脚本、自动化流水线或后台服务中运行的命令行程序，当程序异常终止或返回非零退出码时，需要快速定位故障类别（如参数错误、资源缺失、依赖失败、超时等）并采取相应恢复措施的场景。不适用于交互式调试或图形界面应用。

## 输入
- 程序退出码（exit code）：整数值，通常0表示成功，非0表示失败。
- 标准错误流（stderr）：程序输出的错误信息、警告或堆栈跟踪。
- 操作系统信号（signal）：如 SIGTERM、SIGKILL、SIGSEGV 等。
- 运行环境信息：操作系统版本、依赖库版本、资源使用情况（CPU、内存、磁盘）。
- 输入参数：命令行参数、环境变量、配置文件路径。

## 输出
- 故障类别：如参数验证失败、依赖缺失、资源不足、超时、权限错误、内部崩溃等。
- 根因分析：具体错误原因及可能的影响范围。
- 恢复建议：重试策略、参数调整、环境修复或回退方案。
- 诊断报告：结构化日志，包含退出码、错误消息、堆栈跟踪和环境快照。

## 流程节点
1. **退出码捕获**：在非交互执行后立即获取程序退出码。
2. **标准错误解析**：提取 stderr 中的关键错误信息，过滤无关输出。
3. **信号分析**：若程序因信号终止，识别信号类型及可能原因。
4. **环境上下文收集**：记录运行时的系统资源、依赖版本和输入参数。
5. **分类规则匹配**：将退出码、错误消息和信号与已知故障模式库进行匹配。
6. **根因推断**：结合上下文信息推断最可能的故障原因。
7. **恢复策略生成**：根据故障类别推荐相应的修复或重试措施。
8. **报告生成**：输出结构化诊断报告，供后续分析或自动化处理。

## 关键参数
| 参数 | 值 | 来源 | 说明 |
|------|-----|------|------|
| 退出码语义 | 0=成功，1=一般错误，2=误用shell命令，126=权限问题，127=命令未找到，128+N=信号终止 | POSIX标准 | 不同操作系统可能有差异 |
| stderr 缓冲策略 | 行缓冲或全缓冲 | [论文1] | 影响错误信息的实时捕获 |
| 信号超时阈值 | 通常30秒 | 实践经验 | 用于区分正常终止与挂起 |
| 故障模式库大小 | 取决于具体领域 | [论文2] | 覆盖常见错误场景的模式数量 |

## 边界与分流
- 若退出码不在已知模式中，应记录为“未知错误”并收集完整上下文供人工分析。
- 若 stderr 为空但退出码非零，需检查程序是否将错误写入其他流（如 stdout）或日志文件。
- 若程序因信号终止，需区分是外部强制终止（如 SIGKILL）还是程序自身崩溃（如 SIGSEGV）。
- 在资源受限环境中，诊断过程本身可能失败，需降级到基础日志记录。

## 质量检查
- 验证退出码是否被正确捕获，无遗漏或误读。
- 检查 stderr 解析是否提取到关键错误信息，无噪声干扰。
- 确认故障分类与根因分析的一致性，避免矛盾结论。
- 测试恢复建议在实际场景中的有效性。

## 回退策略
- 若自动分类失败，应保存完整原始输出（stdout、stderr、退出码）供人工审查。
- 提供手动诊断指南，指导用户如何使用调试工具（如 strace、ltrace）进一步分析。
- 在关键系统中，实现故障隔离机制，防止单个程序故障扩散。

## 资源召回建议
当遇到 CLI 程序在非交互环境中异常终止、退出码含义不明、错误信息难以解析时，应召回本卡片。配套资源包括：POSIX 退出码规范、常见错误模式库、结构化日志工具、故障注入测试框架。
